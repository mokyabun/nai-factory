## 문제 목록

이후 문서에서 아래 ID로 참조한다.

### 보안 (재현 확인)

- **S1. `/data/*` 경로 탈출**: `server/src/data.ts:117`. `GET /api/data/..%2Fpackage.json`처럼 요청하면 서버 cwd 아래 파일(`.env` 포함)이 노출된다. `/data/database.db`는 우회 없이도 바로 다운로드된다.
- **S2. API 키 탈취**: CORS 전체 허용 + 인증 없음 + `0.0.0.0` + `GET /settings`가 `apiKey`를 평문으로 반환한다. 아무 웹사이트에서나 키를 읽을 수 있다.
- **S3. 임의 경로 쓰기**: `export.serverPath`를 바꾼 뒤 내보내기를 호출하면 서버의 아무 디렉터리에나 파일을 쓴다.

### 버그 (재현 확인)

- **B1. 절대경로 데이터 디렉터리에서 이미지 404**: Docker처럼 데이터 경로가 절대경로면 DB에도 절대경로가 저장되고, 웹이 만든 URL이 라우트에 맞지 않는다.
- **B2. 변수 순서를 바꾸거나 중간에 끼워 넣으면 500**: `syncVariations`에서 UNIQUE(scene_id, display_order)가 순차 업데이트 도중 충돌한다.
- **B3. 프로젝트 설정 부분 저장 시 나머지가 기본값으로 초기화**: Zod v4는 `.partial()`이어도 `.default()`를 채워 넣는다. `NovelAISettings.mode`도 같다.
- **B4. SSE가 약 12초마다 끊김**: Bun 기본 `idleTimeout` 10초, 하트비트 30초. 재연결할 때마다 NovelAI 상태 API까지 다시 호출한다.
- **B5. 이미지 생성 POST 재시도 설정이 무효**: ky는 기본적으로 POST를 재시도하지 않는다.

### 코드상 문제 (코드 근거)

- **C1.** 작업이 실패한 뒤 재시작하면 처음부터 다시 생성한다(중복 이미지, Anlas 낭비).
- **C2.** 실행 중인 작업은 취소할 수 없다. 실행 중에 씬을 삭제하면 FK 오류로 큐가 "failure" 정지한다.
- **C3.** 트랜잭션 없이 여러 단계를 수행한다(복제, replace 가져오기, stash 적용, 삭제). replace 모드에서 실패하면 데이터가 유실된다.
- **C4.** 이미지 행이 파일보다 먼저 생성된다(`filePath: ''`). 그 사이에 깨진 이미지가 노출된다.
- **C5.** 큐 루프가 끝나는 순간 들어온 작업은 루프를 재시작하지 않는다.
- **C6.** `Parameters` 범위 검증이 없다. `ImagePatchBody.displayOrder`가 임의 값을 받아 UNIQUE 위반 500을 낸다.
- **C7.** zip을 메모리에서 통째로 처리하고, 업로드 크기 제한이 없다.
- **C8.** NovelAI 오류 분류가 메시지 정규식에 의존한다. 일부 fetch에 타임아웃이 없다.
- **C9.** 이미지를 저장한 뒤 파일을 다시 읽어 메타데이터를 계산한다.
- **C10.** 익스포트 파일명의 중복 검사가 불완전하다.

### 스키마/마이그레이션

- **M1.** drizzle 저널·스냅샷과 실제 SQL 파일이 불일치한다(0001/0002는 직접 작성).
- **M2.** 이미 적용된 `0000_initial.sql`을 사후에 수정했고, 그 보정용으로 `ensureNestedGroupSchema`가 생겼다.
- **M3.** `drizzle.config.ts`의 기본 DB 경로가 실제 경로와 다르다.
- **M4.** 시간 형식이 혼재한다: `datetime('now')`(Z 없음)와 ISO+Z. 브라우저에서 9시간 오차가 생길 수 있다.
- **M5.** 경로 문자열과 `assetId`가 함께 저장된다(같은 정보가 두 곳).
- **M6.** UNIQUE 인덱스와 일반 인덱스가 같은 컬럼에 중복되어 있다.
- **M7.** `updatedAt` 처리 방식이 섞여 있다(`$onUpdate`와 수동 갱신).
- **M8.** assets FK에 삭제 정책이 없다(고아 파일·행).
- **M9.** 큐 테이블 2개가 `sortIndex`를 공유한다.

### 구조/도구

- **T1.** 라우트 파일에 DB 쿼리와 비즈니스 로직이 섞여 있다.
- **T2.** 중복 헬퍼: `normalizeProject`, `variationOrder`, `contentType`, `escapeXml`.
- **T3.** 웹 API 경로와 타입을 손으로 적는다(서버와 동기화되지 않음).
- **T4.** 대형 프론트 파일: 프로젝트 페이지 1181줄, 프로젝트 사이드바 817줄.
- **T5.** `latest` 버전 사용, 쓰지 않는 lockfile, `shadcn`이 dependencies에 있음, `@types/node` 버전 불일치.
- **T6.** 테스트 후 `.db` 파일이 남는다.

## 설계 원칙

1. **DB는 단일 진실 공급원.** 파일 경로는 `assets` 테이블에만, 데이터 루트 기준 상대경로로 저장한다.
2. **시간은 DB에 정수(Unix ms, UTC), API에는 ISO-8601 `Z` 문자열.**
3. **다단계 쓰기는 하나의 트랜잭션.** 파일 삭제는 커밋 후에 하고, 실패하면 GC가 회수한다.
4. **요청 스키마와 엔티티 스키마를 분리.** PATCH 스키마에는 `.default()`를 쓰지 않는다.
5. **비밀값은 응답에 포함하지 않음.**
6. **라우트는 얇게**: 검증 → 서비스 → 응답.
7. **마이그레이션은 drizzle-kit 생성물만 쓰고, 적용된 파일은 수정하지 않는다.**
